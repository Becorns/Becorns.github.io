# 概念
## 工作组
工作组是最简单的资源管理模式，通常由不多于10台的计算构成，每个计算机同等地位
## 单域
一个边界。
## 域树
子域父域构成。
通过建立信任关系连接在一起
每个域都有自己的域控，策略
## 域林
多个域树构成。通过信任关系连在一起

# 计算机角色
> 域控，成员服务器，客户机，独立机
* DC
  管理所有的网络访问.
  存储了域内所有的账户和策略信息，
  可以有多台计算机被配置为域控制器
* 成员服务器
  加入了域，安装了服务器组件
  但是没有AD
* 客户机
  用域账号登录后，访问域中各种资源
# 目录
目录是指存储了相关网络对象（如用户、组、计算机、共享资源、打印机、联系人等）的信息集合。
## LDAP
Light Directory Access Protocol，是一个基于X.500标准的轻量级目录服务协议，采用了服务端/客户端模式。
## AD

active Directory，包含域中的将用户，计算机，打印机等资源。
一般部署在域控上。由域控来管理AD
域树共享一个AD，目录内的数据分散存储在各个域中。
* AD功能：
  软件集中管理
  账户集中管理
  环境集中管理
  增强安全性
  

>域和AD是两回事，域是管理网络划分的边界，ad是目录服务
>ad是统一整理资源，是资源对象(用户，组，计算机等)的目录。而这个ad+资源的集合就ad数据库，这个库一般在域控上，身份认证就是ad库中寻找账户资源。
>在windows 2000前，域是没有ad的，DC使用的是SAM库。
>现在的windows server 域和ad是绑定的。

# 域组
默认域用户登录后，是在user组中，
* 域本地组
	用于分配权限，比如目录中有数据服务，创建一个DL_DB组，这个组能访问数据库资源
	这个组的成员可以是全局组，通用组，单个域用户

* 通用组
  和全局组类似，只不过范围从本域，扩展到域林。能接收单用户，全局组。主要作用是管理全局组

# A-G-DL-P
微软推荐的管理策略
A(account)-G(Global Group)-DL(Domain Local Group)-P(Permission)
核心机制：将用户放到全局组，全局组再放到DL中，DL实际分配权限

## Kerberors

### PAC

Privilege Attribute Certificate 权限信息包。包含用户权限信息(rid，id等)，附加凭据等。
PAC包含了服务密钥和KDC密钥进行的两个签名：

* PAC_SERVER_CHECKSUM
* PAC_PRIVSVR_CHECKSUM
  防止不受信任的服务伪造PAC来造ticket


微软把它加到了kerberors中，具体在TGT和TGS中。

> 基于加密Ticket的身份认证协议,引入可信第三方进行身份认证

### 角色

* 客户端:请求访问服务的实体,使用Tikect进行安全通信
* 服务端
* KDC: Key Distribution Center,密钥分发中心,包含组件:
  Authenrication Service(**AS**):认证服务,进行用户信息认证,为客户端提供(Ticket Granting Tickets)TGT
  Ticket Granting Service(**TGS**):验证TGT和Authenticator,为客户端提供 Service Tickets

kerberos基于Tiket。需要先获得TGT，再获得Tiket

### 认证过程


1. 发起AS-REQUEST：
   `Client -> AS: Padata,IDc, Realm, SPN, Options`

   用户想要访问某个访问时，输入账户密码，向AS发送REQ认证请求：

   **预认证**(Padata)：用户密钥(NTLM hash/AES key)加密的时间戳。
   服务器AS收到后，根据用户名找到用户密钥，解密获得时间戳，若能解密，且再一定时间差范围之内，认证通过。
   这里通过密钥(NTLM hash /AES key)加密时间戳，可能造成[PTH](#)或[PTK](#)。预认证可以关闭，如果关闭了预认证，可能造成[AS_REPRoasting]()

   **IDc**:用户名。
   用户名存在与否影响返回内容。->可进行[用户枚举]()。用户存在时，密码的正确与否会影响相应包。->[密码喷洒](#)
   **realm**：域名
   **SPN**：域中服务的唯一标识符，这里向AS发送获得TGT的请求，而TGT由kbrtgt签发，所以这里的SPN为kbrtgt
   **options**:一些和kdc的协商,如加密方法

2. AS-Reply

   > AS接收后，根据IDc去查用户密钥，解密获得时间戳，若在指定范围内，则认证成功。

   AS发送AS-REP给客户端：
   `AS -> C:Enc(Kc, [session key， TS2, Lifetime]),TGT`
   **外层enc_part**(Enc)：Enc(Kc, [session key, TS2, Lifetime]
   $K_c$：用户密钥。
   这是用用户密钥加密的部分，包含用于和TGS会话的密钥(session key)，时间戳TS2，票据时间Lifetime
   **ticket**(TGT)：

   ```json
   Ticket (TGT):
   {
     tkt-vno
     realm
     sname  
     enc-part{session_key,authtime,endtime,cname,PAC}  #只需关注这个.和外层enc_part不同，这是由krbtgt密钥加密的
   }
   ```

   最重要的是内层enc-part(由krbtgt密钥加密)，包含session key，认证时间(authtime)，到期时间(endtime)，PAC。
   PAC包含用户身份权限。
   这里如果能抓到krbtgt的密钥，可以自己制作TGT，即可造成[黄金票据]()

3. TGS_REQUEST:
   客户端接收TGT和enc_part后，解密enc_part，获得session_key。
   向TGS发送请求：
   `C -> TGS: TGT, AuthenticatorC`
   包含TGT，AuthenticatorC(包含session_key加密的时间戳)

4. TGS-REP
   TGS收到后，用kbrtgt密钥解密TGT，得到session_key。用session_key解密获得时间戳和PAC，证明范围有效。
   返回TGS_REP：
   `TGS -> C: Enc_part(session_key, TS4, Lifetime), ST`
   **Enc_part**：session_key加密的数据,包括cname，srealm，Server_session_key(用于服务器认证)
   **ST**：Server ticket，用于访问服务器，

   ```
   Ticket (ST):
   {
     tkt-vno
     realm
     sname  
     enc-part{session_key,sname,PAC等} #主要是这个
   }
   ```

   ST中的enc_part是给服务端的，用服务端密钥加密。

5. 
   客户端收到后，用内存中缓存的session_key，解密，获得Serer_session_key。

   向服务器发送：
   ST，server_session_key加密的时间戳。

6. 服务器收到后，解密ST，获得Server_sesion_key，解密获得时间戳。
   没开启PAC认证的情况下，不会验证PAC中的权限能不能通过ACL。也就是说，默认不会检查用户权限。
   开启PAC的情况，会向KDC通过RPC认证，权限是否有效，再开启服务。

#### 非约束性委派

KDC会把用户TGT发给服务，服务使用TGT访问任意服务。
用户 A 去访问服务B，服务 B 的服务账户开启了非约束委派，那么当用户 A 访问服务 B 的时候会将用户 A 的 TGT 发送给服务 B 并保存进内存，服务 B 能够利用用户 A 的身份去访问用户 A 能够访问的任意服务。
如果攻击者拿下服务，可以伪装为用户访问

#### 约束性委派

服务只能代表用户访问指定服务，KDC不再发给访问TGT，而是引入`S4U` (S4U2Self / S4U2proxy),服务代替用户：
* S4U2self (Service for User to S4U2Self) 可以代表自身请求针对其自身的 Kerberos 服务票据(ST)；如果一个服务账户的 userAccountControl 标志为 TRUSTED_TO_AUTH_FOR_DELEGATION, 则其可以代表任何其他用户获取自身服务的 TGS/ST。
* S4U2proxy(Service for User to Proxy) 可以以用户的名义请求其它服务的 ST，限制了 S4U2proxy 扩展的范围。服务帐户可以代表任何用户获取在 msDS-AllowedToDelegateTo 中设置的服务的 TGS/ST，首先需要从该用户到其本身的 TGS/ST，但它可以在请求另一个 TGS 之前使用 S4U2self 获得此 TGS/ST。

## NTLM

###    LM hash

微软首次引入的认证算法，本质是DES算法，并不安全。
在win NT 3.1开始引入NTLM hash，基于md4。LM hash的明文密码只能在14位之下。所以要使用NTLM，设置密码超过14位。
在win2008，禁用了LM hash。只使用NTLM，为了兼容，并未删除LM，只是禁用。

### NTLm算法实现

```python
NT_Hash=MD4(UTF-16LE(Password))
```

加密后的密码存储在 **C:\Windows\system23\config\SAM**

### 认证过程

NTLM协议基于 Challenge/Response（质询/响应)的过程。
消息有三种：

> * Type 1 (Negotiate，协商)
>   <img src="https://cdn.jsdmirror.cn/gh/Becorns/image/img/20260403100838982.png" style="zoom: 20%;" />
> * Type 2 (Challenge，质询)
>   
>
> * Type 3  (Authentication，认证)



过程如下：

> 工作组环境中

1. 客户端输入密码后,调用LSASS->NTLM SSP ,计算hash,并缓存.然后使用NTLM SSP生成NTLMSSP_NEGOTIATE消息(Type 1)

2. 服务器接收到Type 1后,读取后传入NTLM SSP 得到NTLMSSP_CHALLENGE(Type 2), 返回这个消息并附带16位随机值(challenge 值)，NTLMv1是8位

3. 客户端收到 Type 2后,读取challege.使用 NTLM hash 对challege进行加密(response，加密方法有两个版本).。最后将response+用户名等交给NTLM SSP 得到 Type 3.

4. 服务端收到后,读取challenge,并与自己的对比.判断密码是否正确

> 域环境中

### NTLM版本

> NTLM协议有两个版本:NTLM v1 , NTLM v2 ,用得最多的是 v2

* NTLMv1:

  ```python
  NTLMv1_hash=MD4(UTF-16LE(password))
  response = DES(NTLMv1_hash, challenge)
  ```

* NTLMv2:

  ```
  NTLMv2 Hash = HMAC-MD5(NTLM hash, unicode(hex((upper(UserName)+DomainName))))
  response = HMAC-MD5(NTLMv2 Hash, challenge + blob)
  ```
